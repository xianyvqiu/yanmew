# 颜喵 YanMew 记忆与旅行游记设计

- 日期：2026-09-19
- 状态：核心产品规则、上下文自动缩减及游记独立删除已确认
- 范围：聊天回合、短期记忆、长期记忆的来源、回退与混合检索、消息操作、上下文原文、记事本、旅行游记。

## 1. 基本原则

- 聊天回合、消息、短期记忆、长期记忆、旅行与旅行游记都按会话隔离。任何查询、生成、编辑、回退、导出和导入都必须携带并校验 `session_id`，不能跨会话读取或关联。
- 一轮完整对话是“用户发送一次 + AI 正常回复完成一次”。一轮完整对话对应一条短期记忆。
- 无聊时由 AI 主动发出的消息不是聊天回合，不生成短期记忆。
- AI 回复被中断时，该轮保留为未完整回合，不生成短期记忆，也不参与长期记忆整合。
- **短期记忆和长期记忆是中性事实记录，不使用人设口吻，不需要任何氛围总结或主观评价，必须只是如同剧本一样的叙事描述。**
- 旅行游记不是短期记忆或长期记忆，不参与长期记忆整合。游记使用对应人设的口吻，对整次旅行作比短期记忆更详细的总结。

## 2. 聊天回合与消息

### 2.1 回合模型

- 使用 `chat_rounds` 保存回合，使用 `messages.round_id` 把一条用户消息和对应 AI 回复归入同一轮。
- 用户发送消息时先创建 `pending` 回合并保存用户消息。AI 正常完成回复后，在同一次数据库提交中保存 AI 消息并把回合改为 `completed`。
- AI 回复中断后，已收到的正文仍按现有聊天规则保存一次，回合标记为 `interrupted`；没有正文时不插入空 AI 消息。
- 主动消息的 `round_id` 为 `NULL`，避免它被误计为用户与 AI 的完整对话。

### 2.2 回合与短期记忆

- 每个 `completed` 回合只能绑定一条短期记忆，短期记忆通过 `round_id` 精确关联该轮的两条消息。
- 短期记忆生成失败时保留待生成状态，由后台重试；同一回合不能重复插入多条短期记忆。
- 生成任务读取固定回合、两条消息正文和 `memory_revision` 快照，在 AI 请求结束后重新校验，再提交结果。版本或正文变化表示结果基于旧输入，必须丢弃且不得插入短期记忆。
- 丢弃过期结果后，工作器立即用最新内容重新排队。待生成任务同时通过查询“`completed` 且不存在对应短期记忆”的回合恢复，不把短期记忆的 `integration_state=pending` 当成生成任务状态；因此版本冲突后即使应用关闭，下次启动仍能发现遗漏。`short_memories.round_id` 的唯一约束阻止并发重试落盘两条。
- 同一会话按回合顺序补做；较早完整回合缺少短期记忆时，不跨过它整合后面的记录。长期整合失败或快照过期时，来源短期记忆继续保持 `pending`，由后续调度重试。

## 3. 短期记忆

### 3.1 保存与状态

- 完整回合结束后，由记忆专用 provider 为该轮生成一条短期记忆；未单独指定 provider 时跟随聊天 provider。
- 短期记忆 `content` 的全局字数范围默认是 `12–100` 个中文汉字，用户可在全局设置修改；生成提示和结果校验读取同一设置。
- 短期记忆即使已经整合为长期记忆也不删除，始终作为可追溯的原始记忆保留。
- `integration_state` 只有两种状态：`pending` 表示尚未整合成长期记忆，`integrated` 表示已经整合。
- 短期记忆只来源于聊天回合。旅行内容写入 `travel_journals`，不写入 `short_memories`。

### 3.2 用户操作

- 用户不能手动新建或删除短期记忆，可以手动编辑。
- 每条短期记忆提供“重新生成”按钮：AI 根据该记忆绑定回合的用户消息和 AI 回复重新生成，先显示预览，用户确认后覆盖原内容，记录 ID 不变；确认前重验目标及内容版本，预览生成后又被编辑则提示预览失效。
- 编辑或重新生成已经整合的短期记忆时，不自动改写现有长期记忆；界面提示用户按需对相关长期记忆执行“重新整合”。

### 3.3 自动生成运行契约（Task 9.3 已接通）

- `jobs.rs` 的唯一循环持有 `memory::Worker`，启动、完整回合保存通知及每秒兜底扫描发现缺失记忆。一次只启动一个异步生成任务，不等待模型阻塞桌宠计时或提醒调度；同会话只取最早缺失的完整回合，其他会话可在失败等待期间继续。
- 请求只包含本轮用户原文、AI 原文及中性记录系统约束，要求 JSON `{ "content": "事实概括" }`；不加载人设口吻，不调用工具。优先记忆专用提供商，未指定时跟随聊天提供商；请求复用已有客户端、超时和取消机制。
- 正文按中文汉字计数，标点、拉丁字母与 emoji 不计入 `12–100` 范围；这与记事本按 Unicode 字符统计的软限制不同。空值、无效 JSON、额外字段、非法控制字符、字数不合格或模型非正常结束均不保存，不裁剪结果凑字数。现有客户端的截断错误为 `AI_TRUNCATED`。
- 提交前同时复核会话归属、完整回合、两条消息 ID/正文、`memory_revision`、有效记忆提供商配置及最小/最大字数；已存在短期记忆时直接保留原记录。新增短期记忆和版本递增在同一事务完成，取消、删除或校验失败不留下半条记忆。
- 失败后分别等待 30 秒、120 秒再次尝试，总计最多三次。随后停止该回合的自动重试；用户在记事本小窗点击“重试待生成记忆”只恢复当前会话的缺失任务。有效记忆配置变化、测试当前有效记忆提供商成功或应用重启也会重新尝试。没有可用提供商同样保留聊天与缺失待办，不无限调用。
- 缺失关系持久保存在 SQLite；失败次数、等待时刻和活动标记只保存在本次运行内存，重启重新扫描。取消和过期结果不计为失败；过期结果按最新快照重排。错误仅在生成状态区显示，不使桌宠休眠。
- 当前小窗已显示生成统计与重试，短期/长期内容编辑及预览确认在 Task 9.7 接入；长期整合在 Task 9.4、混合 RAG 在 Task 9.5、完整上下文在 Task 9.6 接入。生成成功不等于当前聊天已经携带记忆。

## 4. 长期记忆的生成、来源与回退

### 4.1 `k+1` 触发规则

- `k` 表示生成一条长期记忆所使用的短期记忆数量。用户可在全局设置中修改，默认值为 `20`。
- 当一个会话出现第 `k+1` 条尚未整合的短期记忆时，才使用它之前连续的 `k` 条尚未整合短期记忆生成一条长期记忆。
- 触发整合的第 `k+1` 条短期记忆不进入本次长期记忆，继续保持 `pending`，作为下一组的起点。
- 整合成功后，前 `k` 条短期记忆改为 `integrated`，但不删除。
- 用户修改 `k` 后，只影响以后尚未整合的短期记忆。既有长期记忆保留生成时的实际来源数量和来源记录，不按新值重算。
- 分组与“最近”均按来源回合顺序确定，不按 AI 请求完成时间或补生成短期记忆的自增 ID 排序。恢复后有多组积压时逐组处理，每组仍由它自己的第 `k+1` 个回合触发；提交前验证来源、触发回合、版本和本次采用的 `k` 未失效。

### 4.2 来源与边界

- `long_memory_sources` 按顺序保存每条长期记忆实际使用的短期记忆 ID；一条短期记忆最多归入一条长期记忆。
- `long_memories.source_count` 保存本次实际使用的 `k` 值。
- 长期记忆的实际覆盖边界不重复保存字段；读取 `long_memory_sources` 中 `source_order` 最大的来源短期记忆，再通过其 `round_id` 定位来源回合及最后一条 AI 消息。
- `long_memories.activated_by_round_id` 保存触发这次整合的第 `k+1` 轮回合 ID，用于删除最后一轮时精确回退。
- 每条长期记忆包含一句简短的 `title` 和一份 `content`。标题与正文在同一次整合请求中生成，标题用于快速识别这段事实，正文保存完整的中性叙事。
- 长期记忆 `content` 的全局字数范围默认是 `150–250` 个中文汉字，用户可在全局设置修改；简短 `title` 不计入正文字数范围。
- 正常整合不删除旧长期记忆。用户不能手动新建或删除长期记忆，可以手动编辑。
- 每条长期记忆提供“重新整合”按钮：严格使用其原有 `long_memory_sources` 同时重新生成标题和正文，先显示预览，用户确认后覆盖，记录 ID、来源关系和覆盖边界不变；确认前重验来源及内容版本，过期预览不得覆盖较新编辑。
- 取消“选择多条长期记忆合并”功能。

### 4.3 永久保存与上下文控制

- 长期记忆在正常流程中永久保存，不因数量增加而自动删除、覆盖、再次合并或压缩。
- 存储数量可以持续增长，每次请求进入 AI 上下文的数量保持有限。长期记忆规模通过检索控制，不通过删除历史控制。
- `recent_long_memory_count` 表示直接进入上下文的最近长期记忆数量 `m`，用户可在全局设置中修改，默认值为 `30`。它与最近聊天原文数量 `recent_message_count` 是两个独立设置。
- 最近 `m` 条长期记忆的标题和正文直接进入上下文；更早的长期记忆使用第 4.4 节的混合检索按需加入。

### 4.4 混合 RAG

- 每次组装聊天上下文时，在当前会话内对 `m` 条以外的长期记忆进行一次快速检索，不额外调用聊天或记忆整合 AI。
- 关键词通道使用 SQLite FTS5，为长期记忆的标题与正文建立 `trigram` 全文索引，适合查找明确出现的人名、地点、书名和连续短语；少于三个字符的查询由 Rust 层使用普通匹配补充。
- 语义通道使用当前 Embedding 提供商把检索文本转换为向量，与当前会话较旧长期记忆的向量计算相似度，从不同措辞中查找意思相关的记忆。
- 两路候选使用排名融合合并，按长期记忆 ID 去重，并排除已经直接加入的最近 `m` 条；只把达到内部相关阈值且未超过候选数量上限与上下文预算的结果加入。
- 相关阈值、候选数量和上下文预算是检索实现参数，通过中文长期回忆测试集校准，不增加普通用户必须理解的设置项。
- 长期记忆数量在第一版规模下直接在当前会话范围内计算向量相似度，不引入独立向量数据库。

### 4.5 Embedding 提供商

- Embedding 提供商独立于聊天 provider 和记忆整合 provider，统一放在“全局设置 > API 提供商 > Embedding 模型”中管理。
- 默认提供并启用 `BAAI/bge-small-zh-v1.5` 本地模型。模型文件作为应用资源随 Windows 便携版一起打包，离线可用，不产生按次接口费用；内置项不能删除。
- 用户可以新增联网 Embedding 提供商，填写名称、base URL、API Key 和模型名，使用 OpenAI-compatible `/embeddings` 接口，并通过“测试连接”确认返回向量有效。
- 切换 Embedding 提供商后，旧向量视为过期并在后台按当前会话优先逐步重建。重建期间 FTS5 仍可检索，已经重建的长期记忆同时参与语义检索。
- 联网 Embedding 会在每次需要检索时产生一次向量接口请求，可能增加回复等待时间；请求失败时本次降级为 FTS5 检索，聊天仍可继续，不进入休眠。

#### 本地 Embedding 运行与资源契约（Task 9.5）

- 默认本地、API 可选；本地使用 ONNX Runtime，通过 Rust `ort` 调用，分词使用与模型资源匹配的 `tokenizers`。仅 CPU 推理，不依赖用户安装 Python、CUDA 或独立模型服务；不在 UI 线程运行推理。
- 发布资源固定为 `resources/models/bge-small-zh-v1.5/`，包含 ONNX 权重、匹配的 tokenizer/config、许可证和资源 manifest。manifest 记录上游模型 revision、每个文件的 SHA-256、模型维度、序列长度、池化/归一化方式、推理库版本和导出方法。不得使用运行期 latest 下载。
- 以官方 FP32 导出作为首次结果校验基准；量化版只有在同一检索样本验证后才能替换，不能无记录地换权重。Task 9.5 一次资源验证锁定 `ort` 与 ONNX Runtime 兼容版本、打包文件清单和实际精度；未验证前不宣称已随包可用。
- 分词/向量语义严格按官方模型资料：查询使用模型推荐的中文检索指令，记忆正文不添加查询指令；池化和归一化必须与导出基准一致。超出模型序列长度的输入不可悄悄当完整内容索引：首版标记该项向量不可用并保留 FTS 检索，后续分块须另行明确版本与融合方式。
- 资源路径通过平台 `AppPaths` 扩展的资源定位能力取得，便携版相对可执行文件定位，开发模式显式指向项目资源目录；不得依赖启动工作目录或用户 PATH 中的 DLL。模型不进入用户备份，向量可重建。
- 后台单一模型实例按需加载、串行处理推理任务；CPU intra-op 线程数取可用逻辑 CPU 数与 4 的较小值，至少 1，使用顺序执行模式并关闭空闲自旋。不得每条消息重新加载或为每会话复制模型实例。
- 首次资源验证记录机器配置、模型文件大小、加载耗时、首条/稳态推理耗时、加载前与加载后进程内存及峰值。测量结果写开发记录，不能凭估计声称固定内存占用；仅做一次必要验证，变更资源后才重测。
- 缺文件、校验失败、运行库不兼容或推理失败时显示 Embedding 局部错误，本次只使用 FTS；不自动上传到联网服务，不阻断聊天，不触发桌宠休眠。用户测试连接/修改配置或重启后再尝试加载，禁止紧密自动重试。
- 模型身份必须包含资源 revision/hash、tokenizer、预处理、维度和池化规则；联网身份包含端点、模型及维度，不含密钥。查询与记忆向量只能在相同身份下比较；换模型后台重建，原记忆文本不变。
- 依据：[模型官方说明](https://huggingface.co/BAAI/bge-small-zh-v1.5)、[ort 项目](https://github.com/pykeio/ort)、[ONNX Runtime 线程配置](https://onnxruntime.ai/docs/performance/tune-performance/threading.html)。运行库版本及模型资产许可证在资源锁定时记录，免费 API 不作为默认本地功能的必要条件。

### 4.6 深层回忆工具

本节工具复用 9.2 的聊天工具注册与执行循环，仅增加处理器，不另建 Agent 框架。

- AI 在已注入的长期记忆仍不足以回答时，可以调用以下只读 function call：`search_long_memories`、`open_long_memory`、`open_long_memory_sources`、`open_chat_round`。
- `search_long_memories` 使用相同的当前会话混合检索，只返回候选 ID、标题和简短匹配信息；`open_long_memory` 读取指定长期记忆标题与正文。
- `open_long_memory_sources` 按 `source_order` 读取该长期记忆的来源短期记忆；`open_chat_round` 再从短期记忆的 `round_id` 打开对应用户消息与 AI 回复。
- 所有工具的 `session_id` 由后端根据发起请求时固定的会话快照注入并校验，AI 不能通过参数读取其他会话。
- 深层回忆允许多一轮或多轮工具调用，受现有 `tool_call_rounds` 上限约束，只在普通上下文和快速检索信息不足时使用。

## 5. 消息操作与记忆一致性

### 5.1 编辑消息

- 用户和 AI 的历史消息都可编辑。
- 编辑只修改消息原文，不自动生成、删除或改写短期记忆、长期记忆和旅行游记。
- 如果该回合尚未生成短期记忆，后续生成时使用编辑后的消息正文。
- 用户需要同步记忆时，在记忆小窗手动编辑短期记忆，或使用对应的“重新生成”“重新整合”按钮。

### 5.2 底部消息与回合删除

- 聊天记录只允许从底部删除。完整回合只在最后一条 AI 消息上显示“删除本轮”，点击后同时删除本轮用户消息、AI 消息、`chat_rounds` 记录和对应短期记忆。
- 如果底部只有一条尚未得到 AI 正常回复的用户消息，只删除该消息和未完整回合。
- 如果底部是中断回合且已经保存部分 AI 回复，允许同时删除本轮用户消息、部分 AI 回复和 `chat_rounds` 记录；中断回合没有短期记忆，不触发已有记忆更新或回退。
- 如果底部是主动消息（`round_id=NULL`），只删除这一条消息，不影响已有短期或长期记忆，不删除前面的聊天回合。任何删除都不得越过实际底部消息。
- 删除前取消目标回合仍未结束的请求；事务内重新校验目标仍在底部，迟到的生成结果不得重新写入已删除回合。
- 删除的最后一轮若是某条长期记忆的 `activated_by_round_id`，同一事务删除该长期记忆，并把它通过 `long_memory_sources` 关联的短期记忆恢复为 `pending`。
- 事务先读取来源 ID 并恢复来源状态，再删除长期记忆及其级联关联，最后删除目标回合；具体顺序见《数据库与持久化设计》第 4.3 节。整会话或整人设删除也通过该节规定的统一删除服务执行。
- 删除事务同时递增 `sessions.memory_revision`。任何一步失败都整体回滚。

### 5.3 重说最后一轮

- “重说”只针对最后一个完整回合。生成上下文时排除该轮旧 AI 回复，保留该轮用户消息一次。
- 重说成功后原位更新同一条 AI 消息与表情，保持原 `chat_rounds.id`，并重新生成同一条短期记忆。
- 如果该短期记忆已经通过 `long_memory_sources` 参与长期记忆，则同时根据各自原有来源重新生成受影响的长期记忆。
- 重说不重复增加亲密度，也不重放旧回复已经提交的有副作用工具调用。
- AI 生成期间不持有数据库事务；提交前校验最后一轮、相关记忆来源和 `memory_revision` 仍与快照一致，最终替换在一个短事务中完成。

## 6. 上下文与三条回复路径

- `recent_message_count` 表示进入 AI 上下文的最近消息原文数量，用户可在全局设置中修改，默认值为 `30`。
- 上下文只读取当前会话的数据。日常聊天和无聊主动消息使用相同的会话级消息、短期记忆、旅行游记标题、记事本、节日和环境信息；两者只在触发方式上不同。
- 尚未整合的短期记忆可以进入上下文；已经整合的短期记忆不再直接进入上下文。
- 如果某条尚未整合的短期记忆所对应的两条消息仍在最近原文范围内，本次不重复加入该短期记忆，避免同一内容出现两遍。
- 最近 `recent_long_memory_count` 条长期记忆直接加入；更早且达到相关条件的长期记忆通过混合 RAG 加入，同一条记忆不得重复出现。
- **普通聊天**：最近原文、符合条件的短期记忆、最近长期记忆以及其他固定会话上下文已经足够，没有检索到需要补充的较旧记忆时，直接进行一次 AI 回复。
- **快速回忆**：程序在主回复前完成 FTS5 与 Embedding 混合检索，把少量相关旧长期记忆加入上下文，再进行一次 AI 回复；不额外调用聊天 AI 做检索判断。
- **深层回忆**：现有上下文仍不足时，AI 使用只读工具逐层查看长期记忆、来源短期记忆和原始聊天回合，允许比普通回复稍慢。

### 6.1 完整请求的组成与顺序

“聊天上下文”不能只理解为 `messages` 中静态拼接的文字。一次完整聊天请求由预检索、消息内容、工具定义和后续工具消息四部分组成：

1. 程序先以本次用户输入及当前对话主题为检索文本，在当前会话最近 `m` 条以外的长期记忆中并行执行 FTS5 与 Embedding 检索；融合、去重、阈值和预算筛选完成后，才开始组装主请求。混合 RAG 是主请求前的本地/Embedding 检索步骤，不是让聊天 AI 先调用一次模型决定搜什么。
2. 初始 `messages` 依次包含：系统规则；时间、地点、天气、当天节日、工具使用说明和当前记忆参数；绑定的用户设定；当前人设；当前会话记事本；最近 `m` 条长期记忆；混合 RAG 命中的较旧长期记忆；尚未整合且未与最近原文重复的短期记忆；最近 5 篇旅行游记标题；最近消息原文；本次用户输入。同一记忆和本次用户输入只能出现一次。
3. 请求的 `tools` 字段同时携带当前场景已经实现并获准使用的工具定义。记忆深层回忆至少包括 `search_long_memories`、`open_long_memory`、`open_long_memory_sources`、`open_chat_round`；记事本和旅行游记工具按对应功能实际完成情况注册。未实现或当前状态不允许的工具不得用空实现占位。
4. AI 发起 function call 后，程序执行受限工具，把 assistant 的工具调用消息及对应 tool 结果作为不可拆分的一组追加到本轮 `messages`，然后继续调用同一聊天模型，直到得到最终回复或达到 `tool_call_rounds`、取消、超时或容量上限。工具结果是动态上下文，不替代初始混合 RAG。

工具执行始终使用发起请求时固定的 `persona_id`、`session_id` 和上下文版本，由后端注入或校验归属；AI 不能借工具参数跨会话读取。整个工具循环复用同一请求 ID、取消信号和输出提交目标。普通聊天与快速回忆的“只调用一次聊天 AI”只计算正文主模型调用，不包含独立的颜文字生成请求；使用联网 Embedding 时还会有一次向量接口请求。进入深层回忆后，每一轮工具调用都会增加一次聊天模型往返。

### 6.2 上下文超限处理

#### 容量来源与自动适配（已确认，待 Task 9.6 接入）

- 模型容量与本次携带内容分别管理；不统一套用 16384 token 输入上限，也不因为模型容量大就塞满历史。最近消息数、最近长期记忆数及混合 RAG 规则继续有效。
- 优先读取提供商针对当前模型/端点返回的能力；其次使用有来源和核对日期的内置模型资料。匹配键必须包含提供商与确切模型，不能只按相似模型名猜测。手动高级配置优先于自动结果。
- 无可靠资料时显示“上下文容量未知”，不要求用户填写、不伪造容量。按既定内容选择规则发送；服务端明确返回上下文超限时，裁减可移除内容后最多自动重试一次。网络错误、认证错误不能作为容量错误处理。
- 自动资料按端点与模型缓存；切换模型/地址后重新解析，不能沿用旧模型能力。模型列表没有容量字段时仍视为未知；不通过反复发送大请求探测容量。
- 有准确 tokenizer 时使用对应计数；否则以序列化请求的 UTF-8 字节数加协议开销保守估算，并标注估算值。估算不是服务端真实 token 数。预算包括工具定义、工具结果及输出预留；每次工具往返重新计算。
- 人设、本次用户输入和必要系统/工具协议完整保护。20000 token 人设在模型允许时完整携带，不自动压缩或截断。仅固定部分已超过已知容量时，本地提示换模型或调整内容；未知容量由服务端明确错误后提示。

- 最近原文条数与最近 m 条长期记忆数是正常容量下的目标；超过提供商模型容量时，允许仅在本次请求减少较旧内容，数据库中的消息、短期和长期记忆均不删除，也不改全局设置。
- 组装时预留回复和工具结果空间。先减少较低相关的额外 RAG 内容，再从较旧的历史消息与记忆中逐项移除；同一项不按半段文字截断，工具调用与结果不能拆散。
- 保留系统约束、人设、当前用户输入与必要工具协议；裁减后再次检查预算。最低必要内容仍超限则提示本次无法发送，不偷偷截断当前用户输入或无限重试。
- 本次确有缩减时向聊天窗返回提示信息：“本次上下文过长，已减少部分较旧内容；历史消息和记忆仍完整保留。”主动消息同样遵守预算，不能靠换触发方式绕过容量限制。

### 6.3 记事本软限制

- `notebook_max_chars` 是会话记事本的 AI 维护目标，默认 `4000` 个中文字符，用户可在全局设置修改。它不是 SQLite 字段长度约束，也不限制用户已有内容的保存。
- 后端把限制值、当前字符数和剩余建议字符数一起提供给 `read_notebook` / `update_notebook` 工具；系统提示明确要求 AI 在该范围内维护整份记事本，而不是每次最多新增这么多字。
- 接近上限时，AI 应先合并重复内容、精简旧段落，再写入新内容。超过上限时不截断、不删除、不拒绝已经形成的完整内容，并在工具结果中标记超限；下一次 AI 修改必须优先整理到限制以内。
- 用户手动编辑和导入造成的超限内容继续完整保存。界面显示当前字数与建议上限并提示“AI 将在后续整理”，不把软限制描述成无法保存的硬上限。
- 字符数按 Unicode 字符统计，不按 UTF-8 字节数或模型 token 数计算。限制只控制记事本体积；上下文仍需遵守第 6.2 节的本次请求容量缩减规则。

### 6.4 最大输出与主动继续（已确认，待实现）

- 聊天最大输出默认 `32768 tokens`，用户可在提供商高级设置修改为正整数。它是一次生成的保护上限，不是目标长度；不保证等于或至少产生一万字，部分模型将推理 token 计入输出。
- 已知服务商最大输出较小时取较小值，并显示配置值、实际生效值及限制来源。已知总容量还需扣除本次输入与安全余量；容量未知则标注未知，不声称已自动识别。模型能力由适配层解释，不能混用 `max_tokens` 与 `max_completion_tokens` 的不同语义。
- 表情、记忆整合等内部任务独立确定输出预算，继续遵守各自正文要求，不一律使用聊天的 32768。设置上限不会要求模型凑满字数。
- 服务端明确返回长度终止时，保存部分正文，回合为 `interrupted`、停止原因为 `length_limit`，显示“已达到本次输出上限”和“继续生成”。正常结束不显示此按钮；不自动续写。
- 继续只允许当前会话尾部该回合，且未被编辑、删除或产生后续消息。复用原用户消息、原 AI 消息与 roundId，新建 requestId；不插入虚构的用户“继续”消息。向模型提供已有回复和只续写剩余内容的指令，返回增量追加到原回复。
- 一次续写仍受本次最大输出限制。再次长度停止仍可主动继续；最终正常结束才将原回合改为 `completed`，完整正文生成一条短期记忆、完整轮次亲密度只结算一次。暂停、失败或重启保留此前已保存正文，不自动继续。
- 续写不重新执行原请求已成功的工具。首版续写请求不开放工具，只延续正文；需要新操作时由用户另发消息。模型可能重复衔接文字，不自动按语义删改用户已看到的正文。
- 若用户放弃继续并发送新消息，旧回合保持 interrupted，不生成短期记忆。长度终止属于不完整输出，不归类为乱码或提供商故障。

### 6.5 流式异常保护（已确认，待实现）

- 连接保护：分别处理首个有效响应、无有效进展和总时长超时；沿用现有超时/取消设施。SSE 心跳和空 delta 不代表有效进展；正文、可识别的推理增量及工具参数增量按适配规则计入进展，不将正常思考误判为空转。
- 重复保护：检查有界滑动窗口内的连续句段重复、短周期循环和新增内容比例；达到足够样本长度并持续命中才自动停止。不能仅凭重复词、标点、颜文字、代码格式或列表结构判定异常。不额外请求 AI 充当检测器。
- 编码保护：先正确增量解码 UTF-8 和拼接 SSE，再检测持续大量替换字符或异常控制字符；跨字节分片不得被错误转成乱码。外语、emoji、数学符号和正常颜文字合法。语义混乱无法用字符规则可靠识别，不能承诺全部检测。
- 工具保护：复用已有轮数上限和请求取消，追加相同参数/相同结果持续无进展的检查；同名工具的不同合法调用不能直接判为循环，写入工具仍需防重复执行。
- 异常时经统一终态入口取消请求、保存部分回复为 interrupted、持久化可读停止原因；不生成本轮短期记忆、不结算完整轮次奖励、不自动重说。已经成功持久化的工具操作保持原结果；异常输出不导致提供商休眠。
- 检测窗口和阈值由一次小样本校准确定，至少包含长正常回复、颜文字、代码、外语、连续重复、错误编码和仅心跳流。阈值集中定义且有单位和说明，不散落魔法数；未达到高置信判据不自动截断正常正文。输出 token 上限与已有超时始终作为独立保护。
- 取消意味着停止本地接收并尽力终止远端请求，不能保证第三方立即停止计算/计费。

## 7. 旅行游记

`travels` 是出行记录表，也是同一次旅行的关联根节点。`travel_journals`、`letters`、`souvenirs` 以及旅行来源 `accessories` 分别以 `travel_id` 关联它；游记不是信件或伴手礼的父记录。删除任一子项不会反向删除出行记录或其他子项，其他任务的完成状态也不因此重置。

### 7.1 生成规则

- 每次正常返回的旅行生成一篇旅行游记；切换会话或人设而取消的旅行不生成游记。
- 游记在出行事实 ready 且礼物快照已保存后生成，读取 travels 的地点、活动时间线、实际起止时间和 gift_snapshot_json；仍存在的往返信件作为可选交流细节。信件或礼物展示行被删除不阻塞生成、不抹除出行事实，也不会被恢复。具体字段与顺序见《数据库与持久化设计》第 6.1 节。
- 游记正文使用对应人设的口吻，完整总结整次旅行；`content` 使用独立字数范围设置，默认 `250–350` 个中文汉字，标题不计入该范围。
- 标题必须是一句话的极精炼概括，同时说明什么时候去了哪里、做了什么、有什么伴手礼、去了多久。
- 生成失败时 `travels.journal_state` 保持 `pending`；应用重启、配置有效提供商或测试连接成功后可以重试。完成或取消后不能重复生成。

### 7.2 删除与并发

- 删除服务以 session_id、travel_id、journal_id 验证归属，在一个短事务中删除目标游记；出行记录及其 journal_state=done 保留，信件、礼物和饰品不变。
- AI 生成结果仅在出行仍为 returned 且 journal_state=pending 时允许 INSERT；禁止使用无条件 UPSERT 复活已删除的游记。
- 编辑只 UPDATE 已存在的游记，校验提交时的旧内容快照；目标已被删除返回 NOT_FOUND，已被其他编辑修改返回冲突，不自动新建。
- 提交删除后广播会话级内容变化，列表、详情和后续上下文查询立即去除该游记。只读工具打开已删除 ID 返回不存在，不从缓存补回。
- 备份允许 done 状态的旅行没有游记行，这表示结果曾生成后被删除；导入不能据此改回 pending。恢复删除前的旧备份仍遵守备份快照内容。

### 7.3 查看与上下文

- 旅行游记在当前会话的出行管理中查看，不显示在记忆小窗中。
- 用户可以编辑游记标题和正文，也可以确认后单独删除游记；不提供 AI 重新生成按钮。删除仅移除该篇游记，保留 travels.journal_state=done，不影响出行记录、信件、伴手礼或饰品，重启不补生成已删游记。
- 日常聊天、无聊主动消息和旅行信件只直接放入当前会话最近 `5` 篇游记的标题，不直接放入正文。
- AI 可使用只读 function call：列出当前会话的旅行游记、按条件查找以前的旅行、读取指定游记正文。工具必须校验 `session_id`，不能跨会话查询。

## 8. 备份、导入与删除范围

- 会话级备份必须一起导出 `chat_rounds`、`messages`、`short_memories`、带标题的 `long_memories`、`long_memory_sources`、`travels` 和 `travel_journals`，并在导入时重映射全部关联 ID。
- `long_memories_fts` 与 `long_memory_embeddings` 都是可重建索引，不进入任何导出包。导入完成后先重建 FTS5，再使用当前 Embedding 提供商在后台重建向量。
- 新建副本或覆盖会话时，回合、消息、记忆来源、触发回合、旅行和游记的引用必须保持闭合；无法精确恢复关联的数据不能猜测绑定。
- 删除会话时级联删除该会话的回合、消息、短期记忆、长期记忆、记事本、旅行游记、节日、饰品、信件和伴手礼；小游戏插件、插件设置、插件存档、游戏局与喵币账单均为全局数据，不受会话或人设删除影响。
- 删除非内置人设时，级联删除其全部会话以及上述会话级数据；系统内置默认人设不可删除。
