# 颜喵 YanMew 小游戏插件生态设计

- 日期：2026-09-19
- 状态：产品规则已确认，尚未进入实现
- 范围：小游戏插件协议、仓库分工、便携版内置插件、喵币权限、本地安装与后续 GitHub 分发

## 1. 已确认的产品规则

- 所有小游戏都使用同一套插件协议，包括随颜喵发布的石头剪刀布；主程序不为石头剪刀布保留一套绕过插件宿主的专用实现。
- 颜喵主仓库保存项目维护者自己发布的小游戏、插件 SDK、插件模板和构建工具。
- 石头剪刀布是主仓库中的第一方插件，并作为便携版自带插件一起发布。
- 第三方小游戏以后进入单独的社区小游戏仓库。社区仓库当前只保留规划，不在本阶段创建。
- 社区仓库启用后，作者通过 Pull Request 提交小游戏；审查和自动检查通过后合并，由用户从 GitHub 手动下载插件包。
- 第一版不做“官方收录”徽标、应用内在线目录、自动连接 GitHub、独立插件网站或网页一键安装。
- 所有插件都可以申请“修改喵币”权限。用户允许后，插件通过 `wallet.changeCoins()` 增减喵币；用户拒绝后，插件仍可纯玩。
- 主程序负责喵币事务、非负余额校验、请求去重和账单记录。插件不能直接访问 SQLite。
- 颜喵原有的每日签到是应用级全局功能，不属于小游戏插件。插件不能创建第二套应用签到、修改全局签到状态或写入签到类型流水。
- 插件协议不提供 `ai.generate()` 或其他 AI 出题、解说能力，也不能读取聊天、记忆、记事本、模型配置或 API Key。

## 2. 仓库分工

平台边界：首版发布和验收面向 Windows。插件协议、设置/存档、游戏局与钱包服务可供未来 Android 复用；宿主通过平台适配创建受限 WebView，并将可信实例映射到插件身份，不能依赖插件自行声明 Windows 窗口标签。Android 文件选择、包安装、触摸操作、直接网络阻断与桥接隔离完成专项验收后，才能声明兼容对应插件包。当前不为移动端改动权限规则、不取消第三方插件机制，也不把“能显示网页”等同于“插件安全兼容”。未来主界面和原生悬浮层共用一个 Rust 钱包入口，不分别结算。

### 2.1 颜喵主仓库

主仓库负责主程序和项目维护者发布的小游戏，规划目录如下：

```text
yanwenzi/
├─ src/                                  # React 主程序前端
├─ src-tauri/                            # Rust 核心与插件宿主
├─ plugins/
│  ├─ sdk/                               # 宿主接口类型、开发辅助工具
│  ├─ template/                          # 新小游戏模板
│  ├─ build/                             # 校验和打包脚本
│  ├─ bundled-games.json                 # 随便携版发布的插件清单
│  └─ first-party/
│     └─ rock-paper-scissors/            # 石头剪刀布插件源码
├─ db/
└─ docs/
```

规则：

- `plugins/first-party/` 只保存项目维护者自己发布的小游戏。
- 第一方和第三方插件使用同一 manifest、宿主 API、存档格式和喵币权限接口。
- 是否随便携版打包由主仓库的 `bundled-games.json` 决定，不能由插件在自己的 manifest 中自行声明。
- 石头剪刀布列入 `bundled-games.json`。以后新增的第一方小游戏可以选择随应用打包，或只在主仓库 Release 中提供下载。
- 主程序发布流程只自动打包清单中列出的插件，避免所有第一方游戏都无条件增加便携版体积。

### 2.2 社区小游戏仓库

社区仓库以后单独建立，暂定职责和目录如下：

```text
yanmew-community-games/
├─ games/
│  └─ <plugin-id>/
│     ├─ manifest.json
│     ├─ src/
│     ├─ locales/
│     ├─ icon.svg
│     └─ README.md
├─ validation/                           # 自动检查规则
├─ build/                                # 统一打包脚本
├─ CONTRIBUTING.md                       # 投稿与审查说明
└─ README.md                             # 游戏列表与下载说明
```

规则：

- 第三方作者向 `games/<plugin-id>/` 提交 Pull Request；一个 PR 只新增或更新一个小游戏。
- 作者提交源码、manifest、图标、说明和必要素材，不能只提交无法审查来源的成品包。
- 自动检查通过后再进行人工审查；合并表示允许它进入社区仓库供用户下载，不在颜喵界面授予“官方”身份。
- 社区仓库使用统一构建流程生成 `.yanmew-game`，避免每个作者使用不同打包规则。
- 推荐按 `<plugin-id>/v<version>` 创建 tag 或 Release，并生成 `<plugin-id>-<version>.yanmew-game`。
- 社区仓库未创建前，不在主仓库接收第三方小游戏代码，防止主程序 PR、Issue、CI 和第三方游戏更新混在一起。

## 3. 第一版范围

第一版实现可工作的插件基础，而不是把石头剪刀布伪装成普通内置页面：

- 版本化插件 manifest。
- 插件包校验、安装、启用、停用和卸载。
- 受限插件 WebView 与宿主桥接。
- 插件私有设置和存档。
- 游戏局创建、完成和战绩记录。
- `wallet.modify` 权限与 `wallet.changeCoins()`。
- 按 manifest 中 HTTPS origin 逐项授权的 `network.fetch()` 宿主代理。
- 从本地 `.yanmew-game` 文件安装插件。
- 石头剪刀布插件的构建、随包分发、首次注册和运行。

第一版不实现：

- 在应用内请求 GitHub API、浏览仓库或检查 Release 更新。
- 应用内在线插件目录和“官方收录”徽标。
- 独立插件网站。
- `yanmew://install?...` 网页一键安装。
- 社区仓库的实际创建和运营。

用户将来可以从浏览器打开社区仓库，手动下载 `.yanmew-game`，再使用第一版已经具备的“从本地安装”能力导入颜喵；因此社区仓库上线不要求立即修改颜喵的联网功能。

## 4. 石头剪刀布插件

### 4.1 源码与构建

- 源码位置：`plugins/first-party/rock-paper-scissors/`。
- 插件 ID 固定为 `com.yanmew.game.rock-paper-scissors`，发布后不修改。
- 游戏界面、用户出拳、系统随机出拳、胜负判断和结果展示都在插件边界内完成。
- 随机数由 `game.random()` 提供；游戏局保存必要的随机结果，便于诊断重复结算或异常战绩。
- 构建流程先按普通插件生成 `.yanmew-game`，再由便携版打包流程把同一个包放入应用资源。不能维护“开发版内置代码”和“外部插件包”两份实现。

### 4.2 便携版首次启动

1. 主程序读取随包插件清单并校验石头剪刀布插件资源。
2. `game_plugins` 没有该插件时，登记当前内置版本；已经登记时按版本规则更新。
3. 内置插件显示“随应用提供”，不显示“官方收录”。
4. 内置插件的程序文件不能在游戏管理页永久卸载，因为应用资源中始终存在；用户可以停用插件并清除它的私有存档。
5. 应用升级携带新版本时，先完成兼容检查和插件数据迁移，再切换登记版本；失败时保留可运行旧版本，或禁用并显示具体错误。

### 4.3 喵币权限与纯玩模式

石头剪刀布需要申请 `wallet.modify`，但作为随包插件没有普通安装确认页。因此第一次打开游戏时显示权限确认：

- 每天最多 20 局，无论是否授权喵币都执行同一次数限制。
- 允许：使用原定规则结算，胜利 `+5`、失败 `-4`、平局 `0`，开始前余额至少 4。
- 拒绝：进入纯玩模式，胜负仍正常记录，但本局不增加或扣除喵币，也不受“余额至少 4”的限制。
- 稍后修改：用户可在游戏管理页开启或撤销权限；新增授权只影响之后开始的游戏局，撤销则立即阻止尚未提交的钱包请求。

游戏局开始时保存本局是否具有钱包权限。撤销权限后拒绝尚未发生的钱包请求，本局按纯玩结束；已经提交成功的账单不回滚。

## 5. 插件包与 manifest

插件包扩展名为 `.yanmew-game`，内部至少包含：

```text
example.yanmew-game
├─ manifest.json
├─ ui/
│  ├─ index.html
│  └─ assets/
├─ locales/
│  └─ zh-CN.json
└─ icon.svg
```

manifest 的稳定字段：

- `id`：全局稳定插件 ID，建议使用反向域名格式。
- `name`、`description`、`author`：用户可见信息。
- `version`：插件版本。
- `api_version`：所需宿主协议版本。
- `entry`：插件入口页面。
- `permissions`：申请的权限列表，例如 `wallet.modify`、`network.fetch`。
- `network_origins`：申请联网时必填的 HTTPS origin 列表，格式为协议、主机和可选端口，不接受路径、通配符、用户名或密码。
- `settings_schema`：插件设置项定义。
- `storage_version`：插件私有数据结构版本。
- `homepage`：可选的项目主页。
- `repository`：源码仓库地址；通过主仓库或以后社区仓库分发的插件必须填写 GitHub 仓库地址，本地开发或私人插件可以留空。
- `release_page`：可选的 GitHub Release 或其他人工下载页面。颜喵只保存和展示该链接，不在第一版中自动下载插件包。

manifest 中的权限声明只是申请，不代表用户已经授权。`bundled`、审查状态或未来目录展示状态由分发仓库和主程序决定，不接受插件自报。

## 6. 插件宿主

插件运行在独立的受限 WebView 中，通过带版本号的桥接访问主程序。插件不能取得数据库连接、任意文件路径、系统命令或 Tauri 全部命令。

小游戏插件的视觉与颜喵主程序主题相互独立。亮色、暗色或跟随系统只影响主程序窗口；宿主不向插件注入主题 CSS、不发送主题变化事件，插件作者自行决定游戏界面的颜色与样式。

第一版宿主接口：

- `game.ready()`：通知宿主插件已经准备完成。
- `game.getContext()`：取得语言、游戏局 ID、插件版本、当前授权摘要，以及 manifest 默认值与用户覆盖值合并后的只读插件 `settings` 对象；不包含人设、会话、颜喵主题、主程序全局设置或颜色变量。
- `game.random()`：取得宿主生成的随机数。
- `game.complete(outcome, details)`：结束游戏局并保存标准结果和可选明细。
- `storage.get(key)`、`storage.set(key, value)`、`storage.delete(key)`：访问当前插件自己的 `data_key → JSON value` 命名空间存档。
- `wallet.getBalance()`：读取全局喵币余额。
- `wallet.changeCoins(request)`：在获得 `wallet.modify` 授权时申请喵币变化。
- `network.fetch(request)`：在指定 HTTPS origin 获得 `network.fetch` 授权后，由宿主代发受限网络请求。
- `game.close()`：请求关闭小游戏窗口。

钱包接口只产生插件游戏类型账单，不允许插件伪装成每日签到、节日签到、饰品制作或饰品卖出等主程序业务来源。

协议明确不提供 `ai.generate()`。如果以后出现必须使用 AI 的独立玩法，再作为新权限和新协议版本重新讨论。

## 7. 安装与权限

### 7.1 本地插件安装

1. 用户选择 `.yanmew-game`。
2. 主程序校验包结构、manifest、路径、文件类型、解压大小和 `api_version`。
3. 安装页显示名称、作者、版本、来源、全局存档说明、申请权限和逐项联网来源。
4. “可修改喵币”必须单独说明插件可以增加或扣除全局余额。
5. 用户允许或拒绝每项可选权限后完成安装；拒绝 `wallet.modify` 不影响安装。
6. 新版本先写入临时目录，检查和数据迁移成功后原子切换；失败继续使用旧版本。

插件更新没有增加权限时可以沿用已有授权；新增权限必须重新确认。用户可以随时在游戏管理页撤销权限。

### 7.2 `wallet.changeCoins()`

调用至少携带：

```text
request_id    本次钱包操作的唯一 ID
game_run_id   当前游戏局 ID
delta         整数；正数增加，负数扣除
reason        供用户查看的简短原因
details       可选的结构化游戏明细
```

主程序先验证调用来自对应插件宿主身份，并按 (plugin_id, request_id) 查询是否已提交。已提交且游戏局、数量、原因一致时仅返回原账单，不执行新变化；不一致则返回冲突。新请求再验证插件已启用、当前版本一致、游戏局仍运行、开局时具有钱包权限且当前仍授权、游戏局归属、合法整数变化及非负余额。纯玩局不能因中途授权变成结算局。随后在同一 SQLite 事务中：

1. 写入或更新游戏局的喵币变化。
2. 插入带插件 ID、插件版本、游戏局 ID 和 `request_id` 的账单。
3. 更新全局余额。

任何一步失败都回滚。同一插件内的同一 `request_id` 携带相同业务内容重试时返回原结算结果，不能重复到账或扣款；同 ID 携带不同游戏局、变化数量或原因时返回冲突，不将它视为成功重试。数据库以 `(plugin_id, wallet_request_id)` 唯一约束兜底，避免不同插件的请求编号互相冲突。

成功返回包含账单 ID、已应用变化量、是否重复请求和查询时的当前余额；当前余额不冒充历史结算时余额。调用先完成钱包结算，再结束游戏局；关闭或完成后的新钱包请求拒绝，已提交请求仍可按幂等规则查证，不重复结算。

项目开源且钱包位于用户本机，这套机制用于保证数据一致、隔离插件和提供清楚账单，不承诺阻止电脑所有者主动修改程序或数据库。

### 7.3 `network.fetch()`

- 插件只有在 manifest 同时声明 `network.fetch` 和 `network_origins` 时才能申请联网；未声明、未授权或已撤销时，宿主直接拒绝请求。
- 安装与更新界面按 origin 分项展示，例如 `https://api.example.com`。用户可逐项允许或拒绝；新增 origin 必须重新确认，旧授权不能覆盖新来源。
- 插件 WebView 的内容安全策略禁止直接联网。请求只能通过宿主接口发出，宿主校验插件 ID、当前版本、权限、URL scheme、目标 origin、方法、超时和大小限制。
- V1 只允许 HTTPS，不允许 `file:`、`data:`、`javascript:`、本机回环地址或局域网私有地址。发生重定向时重新校验每一跳，跳到未授权来源立即停止。
- 宿主不会向插件附加颜喵的聊天/Embedding/天气 API Key、Cookie、Windows 凭据或其他插件数据。插件需要的公开服务凭据只能由插件自行向用户说明并保存在自己的全局私有存档中。
- 联网失败只影响该插件本次请求，不让桌宠进入休眠，也不影响主程序聊天与其他插件。

## 8. 当前数据模型

以下结构已经加入完整 V1 `db/schema.sql`。阶段 13 只实现仓储、宿主、界面和旧库版本化迁移，不再临时设计另一套表。

- `game_plugins`：当前插件登记，保存插件 ID、名称、简介、作者、安装版本、API/存储版本、来源类型、相对包路径、包校验值、GitHub 仓库 `repository`、项目主页 `homepage`、Release 页面 `release_page`、manifest 声明的 HTTPS origin、是否随包提供、程序包状态、启用状态和安装/更新时间。程序包状态区分 `available` 与 `missing_package`，缺包时必须停用。
- `game_permissions`：插件 ID、权限名、权限作用域、`pending/allowed/denied` 状态、决定时间和对应插件版本。`wallet.modify` 的作用域为空；`network.fetch` 每个 HTTPS origin 保存一条状态。`pending` 没有决定时间且不能调用权限；新增权限、导入的独立插件数据或新增 origin 默认待确认，manifest 不能替用户授权。
- `game_runs`：不可因插件卸载而删除的全局历史游戏局，保存插件 ID、名称、版本、钱包授权快照、状态、结果、JSON 明细、累计喵币变化、开始和结束时间。它不外键关联当前插件登记，也不保存人设或会话 ID。
- `game_plugin_settings`：插件 ID、设置键、JSON 值和更新时间。石头剪刀布的每日 20 局、胜 `+5`、负 `-4` 是第一版插件固定规则，不作为用户可改的全局设置。
- `game_plugin_data`：插件 ID、数据键、JSON 值、存储版本和更新时间。全部为应用全局的插件私有存档，只按插件 ID 隔离，不随人设或会话切换、删除。
- `currency_ledger`：插件钱包统一使用 `reason=plugin_game`，保存游戏局 ID、插件 ID、插件版本、给用户看的原因和钱包请求 ID。插件 ID 与版本是历史快照，游戏局使用 `RESTRICT` 外键保护。

### 8.1 插件键值与 JSON 字段约定

主程序全局 `settings.key/value` 的允许键和默认值统一登记在《数据库与持久化设计》第 2.7 节。插件不能写入该表，只能使用自己的设置和存档命名空间。

插件键使用稳定的小写英文标识，允许用点号划分用途，例如 `audio.volume`、`stats.overall`。发布后不能在没有迁移的情况下改变旧键含义。键不存在表示“没有用户覆盖值”或“尚无该项存档”，不能用空字符串混淆未设置状态。

`manifest.settings_schema` 中每个设置项可声明：

- `key`：稳定设置键，例如 `audio.volume`。
- `title`、`description`：设置页显示名称与说明。
- `type`：`boolean`、`integer`、`number`、`string` 或 `enum`。
- `default`：插件默认值；数据库没有覆盖行时使用该值。
- `required`：是否必须提供值。
- `minimum`、`maximum`：数字类型的可选范围。
- `options`：`enum` 的可选值及显示文字。

常见的 `game_plugin_settings.setting_key → value_json` 可以是：

```text
audio.enabled                 → true
audio.volume                  → 80
game.difficulty               → "normal"
game.confirm_action           → false
accessibility.reduce_motion   → false
```

这些只是通用示例，不要求每个游戏都有这些设置。`value_json` 可以是 JSON 布尔、数字、字符串、数组或对象，但必须符合本插件 manifest 对该键的声明。宿主设置界面读取 schema 渲染控件，写入前由 Rust 校验键存在、类型、枚举和数值范围。

常见的 `game_plugin_data.data_key → value_json` 可以是：

```text
progress.main        → {"level":3,"checkpoint":"forest-2"}
stats.overall        → {"wins":12,"draws":3,"losses":8,"best_streak":4}
records.high_scores  → [{"mode":"classic","score":1200}]
unlocks.items        → ["blue_board","cat_badge"]
tutorial.state       → {"completed":true,"step":5}
state.current        → {"mode":"timed","remaining_seconds":42}
```

存档键不要求全部在 manifest 中预先列出，因为不同游戏的进度结构差异很大；插件负责其业务格式和 `storage_version` 迁移，主程序负责插件 ID 隔离、合法 JSON、容量限制与备份。插件不得把全局喵币余额、账单、权限决定或宿主强制规则写进私有存档后当作权威数据。

`game_runs.outcome` 保存插件定义的稳定结果标识，例如石头剪刀布使用 `win`、`draw`、`loss`；`details_json` 保存该局的可审计明细。例如：

```json
{
  "schema_version": 1,
  "mode": "classic",
  "player_choice": "rock",
  "opponent_choice": "scissors",
  "result": "win",
  "duration_ms": 1840
}
```

`details_json` 可以因游戏不同增加得分、关卡、随机结果或回合统计，但不能直接决定喵币是否到账。钱包授权、实际 `coin_delta` 和账单以宿主验证后的 `game_runs`、`currency_ledger` 与 `user_state` 为准。石头剪刀布每日 20 局也由历史游戏局按本地日期统计并由宿主执行，不能使用可覆盖的插件私有存档充当权威计数。

插件登记、权限、设置、私有存档、游戏局、钱包和账单都是全局数据。当前插件登记、权限、设置和私有存档可以由用户明确清除；历史游戏局和账单始终保留。随包石头剪刀布由首次启动种子逻辑登记到 `game_plugins`，与本地安装插件走同一套权限、游戏局、存档和钱包结构。

## 9. 游戏中心

第一版游戏中心负责：

- 展示随应用提供和用户本地安装的插件。
- 显示名称、作者、版本、来源、简介、源码链接、全局存档状态、喵币权限、申请的联网来源和逐项授权状态。
- 启动、停用、启用和卸载可卸载插件。
- 开启或撤销喵币权限。
- 按 HTTPS origin 开启或撤销联网权限。
- 查看战绩和插件产生的喵币账单。
- 单独备份或导入插件使用数据；导入摘要明确提示不会恢复历史账单或改变喵币余额，钱包和联网权限需要重新确认。
- 从本地 `.yanmew-game` 文件安装或更新插件。
- 对从备份恢复但尚未重新安装的插件显示“缺少插件包”数据卡片，列出插件名称、插件 ID、原版本、作者、存档是否存在，以及备份中保存的 GitHub 仓库或 Release 页面。
- “打开来源页面”只调用系统默认浏览器；颜喵第一版不请求 GitHub API、不检查更新，也不自动下载或安装。
- 缺少插件包时允许用户选择本地 `.yanmew-game` 重新安装，或删除保留的插件设置与私有存档。插件包安装成功且插件 ID 一致后，再按存储版本执行兼容检查并关联原数据。

随包石头剪刀布插件允许停用和清除私有存档，不允许永久卸载。普通本地插件卸载并保留数据时，清空包路径、标为 `missing_package` 并停用，同时保留登记、授权、设置和私有存档；选择“同时清除插件私有数据”时删除当前登记及其级联数据。历史游戏局和喵币账单不能因卸载或清除当前数据而删除。

## 10. GitHub 人工分发

第一版不由颜喵直接连接 GitHub。用户通过浏览器下载，再从本地安装：

```text
项目维护者的小游戏
    主仓库源码 → 主仓库 Release → .yanmew-game

以后的第三方小游戏
    社区仓库 Pull Request → 自动检查 → 人工审查
    → 合并 → 社区仓库 Release → .yanmew-game

用户
    浏览器下载 → 颜喵“从本地安装” → 权限确认 → 游戏中心
```

这一流程不需要插件网站、在线目录或 GitHub API，也不妨碍以后增加这些能力。

## 11. 后续版本

等主程序插件机制和社区仓库运行稳定后，再讨论：

- 颜喵直接读取 GitHub Releases、检查更新和下载安装。
- 独立轻量插件网站。
- 应用内插件目录。
- “官方收录”或其他推荐徽标。
- `yanmew://install?...` 网页一键唤起颜喵。

这些能力应复用现有 `.yanmew-game`、manifest、权限和安装流程，不能要求小游戏重新打包。

## 12. 备份与后续实施边界

已经确认：

- 全量备份只保存插件使用数据，以及识别这些数据来源所需的登记快照：授权、设置、私有存档、游戏局、相关喵币账单、插件 ID、名称、作者、原版本和来源链接。登记快照不代表插件已经安装。
- 插件管理支持单独导出“插件使用数据包”。包内只保存所选插件的登记快照、来源链接、manifest 声明的权限及联网 origin、设置和私有存档；不保存插件程序包、游戏局、插件账单或全局钱包余额。
- 独立插件数据导入按插件 ID 展示将恢复的设置和存档，用户确认后原子替换所选插件的现有设置与存档。它不导入插件账单、不导入游戏局、不修改当前喵币余额，也不重放任何历史喵币变化。
- 独立插件数据导入后，`wallet.modify` 与每个 `network.fetch` origin 都写为 `pending`；旧包中的允许或拒绝结果只用于说明曾申请过什么权限，不能恢复为有效授权。插件重新安装或打开时，由用户重新允许或拒绝。
- 全量备份不包含用户自行安装的 `.yanmew-game` 程序包；恢复后由用户自行重新下载并安装。
- 插件的本机包路径不进入备份；恢复后的第三方插件登记先标为 `missing_package`，重新安装相同插件 ID 且兼容检查通过后才写入新的本机路径。
- 插件登记同时备份名称、插件 ID、作者、原安装版本、来源类型、包校验值，以及 manifest 提供的 `repository`、`homepage` 和 `release_page`。这些链接用于帮助用户找回插件，不代表颜喵自动联网下载。
- 恢复时即使插件程序包缺失，也保留其登记、授权、设置、私有存档、游戏局和历史账单，并在插件管理中显示“缺少插件包”；重新安装相同插件 ID 后才允许继续运行。
- 来源链接缺失时，插件管理仍显示插件 ID、作者和原版本，并提示用户自行寻找安装包。
- 主程序 API Key 排除规则不等于扫描和删除插件自定义 JSON 中的未知凭据。插件自己的设置与存档按原数据备份，导出说明明确这一边界。
- 卸载或停用插件不能删除历史游戏局和喵币账单。
- 石头剪刀布程序包随应用提供，不依赖联网恢复。
- 插件数据全部属于全局，可以进入全量备份或独立插件使用数据包；人设资料包、人设完整包、会话包和用户设定包都不包含插件登记、授权、设置、存档、游戏局或插件账单。

进入插件开发阶段后，以下工程参数必须通过实现与安全测试定稿：

- 插件允许的资源格式、单包/解压/存档/网络响应大小限制、WebView 内容安全策略，以及 manifest、settings_schema 与桥接请求/响应的版本化 JSON Schema。SDK、模板与宿主共用，不能各自定义不兼容格式。

建立社区插件仓库时再确定正式名称、维护规则和 GitHub Actions 发布格式；这些发布流程不属于首版本地插件宿主的实现前提。

实施时按[实施接口与验收约定](实施接口与验收约定.md)第 4.6 节验证宿主身份、重复结算、权限撤销、插件更新与运行中导入的竞态。社区仓库尚未建立不阻塞首版本地插件机制。
