# 邮件提醒设计

> 当前实现基线（2026-11-09）：源码及备份v26，最新正式包20261109-115108为v26。本文中的阶段版本仅说明引入历史；实际交付范围与默认值见[当前实现与版本范围](当前实现与版本范围.md)。


## 1. 目标与已确认规则

通用设置提供“邮件提醒”模块；用户配置自己的SMTP服务，接收验证码并绑定自己的收件邮箱。无需颜喵服务器，SMTP发送不依赖颜喵服务器；在线到点提醒会按v25流程调用聊天模型生成角色话语，失败用默认文案。验证码与离线汇总不因此额外调用模型。

已确认：应用运行时，到点立即展示界面提醒并自动完成本次触发；角色话语就绪后，同一文案用于聊天和邮件。SMTP发送不阻塞界面。关闭应用无法发送；重开后以一封邮件汇总离开期间过期的事项，循环提醒同一事项只列一次。网络失败有限重试，最终失败在通用设置显示原因并允许重试。

已确认的配置体验要求：发信邮箱与收信邮箱分别填写，收信邮箱不自动代填；引导用户获取发信邮箱授权码，其余可推导的发信配置默认预填。工程方案已确认并接通：lettre 0.11.23、两张邮件队列表、v9正式迁移、通用设置验证码绑定及后台发送。真实SMTP收件仍需用户配置后验证。

## 2. 通用设置界面与操作

### 2.1 基础流程尽量少填

“通用”中提供“邮件提醒”卡片，包含横向滑动开关、绑定状态、收信地址、最近发送状态与配置按钮。常规首次配置要求用户分别填写发信邮箱、发信邮箱授权码、收信邮箱；发送后再输入收到的6位验证码。邮箱类型根据发信邮箱完整地址自动识别，不要求用户先理解SMTP或先选服务商。开关使用按钮及role=switch/aria-checked，轨道、滑块与已开启/已关闭文字保持同排，不受通用表单输入框宽度影响；窄窗允许标题和整个开关换行，不拆分开关文字。

流程为：填写发信邮箱 → 展示对应授权码引导 → 粘贴发信邮箱授权码 → 填写收信邮箱 → 点击“发送验证码” → 在收信邮箱获取验证码 → 输入验证码 → 点击“验证并开启”。无需额外先保存配置、另做一次连接测试或重复填写SMTP账号。发送验证码本身就验证SMTP连接。

正常配置界面显示独立的发信邮箱、授权码、收信邮箱及各自说明、“如何获取授权码”、发信服务器自动配置摘要和发送验证码按钮，以及发送后才出现的验证码输入。收信邮箱首次为空，必须用户填写；允许与发信邮箱相同，也允许不同。验证码和未来提醒均发送到填写的收信邮箱，不需要收信邮箱的授权码。绑定成功后提示已开启；未验证成功开关禁用并显示原因。

### 2.2 自动默认配置与高级设置

- @qq.com：预填smtp.qq.com、465、隐式TLS；登录账号及发件邮箱取用户输入的完整邮箱地址。
- @163.com：预填smtp.163.com、465、隐式TLS；登录账号及发件邮箱取完整邮箱地址。
- @126.com：预填smtp.126.com、465、隐式TLS；登录账号及发件邮箱取完整邮箱地址。
- 收信地址独立填写，首次为空，不默认等于发信邮箱；更改发信邮箱或恢复推荐配置均保留已填写的收信地址。已有保存地址继续读取，不因界面调整清空。发件显示名默认“颜喵提醒”；正文、主题格式和超时使用程序默认值，不要求用户填写。
- 无法识别的邮箱进入“其他邮箱”，只额外要求填写必需的SMTP主机；端口、加密方式等仍预填默认值。不能根据域名直接猜smtp.域名，也不能把企业邮箱或别名冒认成已验证预设。
- 服务器、端口、加密方式、SMTP登录账号和实际发件地址放在默认折叠的“高级设置”里；收信邮箱保留在基础表单，不重复放在高级设置。SMTP服务器是发信服务商提供的域名，例如smtp.qq.com，不是邮箱地址或网页链接；未知邮箱的必填服务器输入旁直接说明到发信邮箱官网的SMTP/客户端设置查询。SMTP登录账号通常为完整发信邮箱，自动预填；仅服务商另有要求时修改。实际发件地址通常同发信邮箱，只有服务商允许的别名发信等情况才改。不要求POP/IMAP收信服务器，不实现读取用户邮件。
- 高级设置支持465隐式TLS与587 STARTTLS；选择标准加密方式时，在用户没有自定义端口的情况下同步常用端口。保持证书验证，不回退明文连接。
- 用户更改邮箱时，自动项跟随更新；已手动覆盖的高级项不能悄悄覆盖，提示其仍为自定义配置，可主动点“恢复推荐配置”。高级字段修改后明确展示自定义状态。

### 2.3 授权码获取引导

输入邮箱后就能看到对应简短步骤及“打开邮箱网页”“打开官方帮助”按钮，不能只放一个模糊的“请输入SMTP密码”。按钮复用现有系统浏览器打开能力，颜喵不代登录邮箱、不操作短信/扫码验证。

QQ邮箱：引导用户打开网页版邮箱，在设置中查找账号、SMTP或客户端授权码相关入口，开启客户端SMTP服务，按邮箱要求完成验证并生成授权码，然后复制到颜喵。新旧网页版入口名称可能不同，文案给出“SMTP”“授权码”等查找关键词；提供官方帮助中心，不能将已失效的旧文章深链接伪装为直接教程。

网易163/126邮箱：引导用户在网页版设置中找到POP3/SMTP/IMAP或客户端授权密码，开启包含SMTP的客户端服务，完成邮箱要求的身份验证并获取客户端授权码，再复制到颜喵。

其他邮箱：提示在该邮箱服务商的账号安全、应用专用密码或SMTP帮助中获取凭据。没有经过验证的提供商不编造具体菜单或授权码地址。

引导旁明确写：邮箱授权码用于连接你的发信邮箱，不是邮箱登录密码；下一步收到的6位验证码用于确认你能收到邮件，两者不同。获取授权码的安全验证由用户在邮箱官网完成，颜喵不收集邮箱登录密码。错误提示分别说明账号/授权码不匹配、未开启SMTP、服务器不可达或验证码错误，不能全部笼统写连接失败。

### 2.4 绑定与配置变更

验证码10分钟有效、重新发送间隔60秒、连续输错5次失效。使用系统安全随机数，验证码不写日志、不进入备份，待验证挑战仅保留在当前运行内存。重启后可重新发送；已完成绑定正常持久化。

修改邮箱、服务器、登录账号、发件/收件邮箱或授权码后，旧绑定失效并关闭发送，必须重新验证。普通关闭开关保留配置与绑定状态，再次开启未变化配置无需重复验证。

授权码不回显；编辑留空保留旧值，替换、清除使用明确操作。用户关闭后停止新的邮件任务，待发送任务取消；已被SMTP服务器接收的邮件不能撤回。

官方/原始帮助依据（预设及引导上线前再次核对）：[腾讯官方客户端配置说明](https://cloud.tencent.com/document/product/1270/55456)、[常见SMTP配置](https://intl.cloud.tencent.com/zh/document/product/1266/71700)、[QQ邮箱帮助中心](https://service.mail.qq.com/)、[网易客户端设置说明](https://help.mail.126.com/faqDetail.do?code=d7a5dc8471cd0c0e8b4b8f4f8e49998b374173cfe9171305fa1ce630d7f67ac25c12dcb3d46222b6)、[163授权码操作说明](https://consumer.huawei.com/cn/support/content/zh-cn15872099/)。其中QQ官方旧版授权码文章当前跳转帮助首页，界面使用可用官方入口及文字步骤，发布时复核具体菜单。

## 3. 发送内容与调度

普通提醒标题：“[颜喵] 提醒：{提醒名称}”。正文显示原提醒名称、详情和原定时间，时间跟随电脑当前时区；在线触发先完成本次提醒并立即显示默认话语，后台生成并保存角色提醒后，邮件正文加入同一句话；生成失败仍使用完整的默认提醒。循环规则继续安排下一次，宠窗“知道了”仅收起本次弹窗。

离线汇总标题：“[颜喵] 你离开期间有事项过期”。正文列去重事项名称、详情及相关时间，与现有离线界面补提醒使用同一批真实触发记录。一次启动的离线汇总合为一个发送任务，不逐个轰炸邮箱；已发出的同批不因打开/关闭设置页再次发送。

只从本次启用开始登记邮件提醒，不补发启用前全部历史记录。邮件发送在后台执行，界面气泡、完成状态和用户聊天不会等待SMTP。发信失败不让桌宠进入提供商休眠，也不改变提醒完成状态。

## 4. 数据库方案与表间关系

连接配置和绑定状态复用全局settings表，授权码通过现有Windows DPAPI加密；不建第二套提供商表，不占用聊天/记忆/生图/识图用途。

实际全局键为reminder_email_config（非密钥JSON）和reminder_email_secret（DPAPI密文）。前者version=1，connection包含email（基础发信邮箱）、host、port、encryption、username（SMTP登录账号）、from（实际发件地址）、to（独立收信邮箱）；新表单to为空且须用户填写，username/from默认随email预填。另有revision=0、enabled=false、verified=false、enabledSince=null。配置字段、加密模式枚举和默认值同步写入schema.sql注释及数据库设计。验证挑战在内存中将配置、revision和密文一起计算SHA-256指纹，旧配置验证码不能验证新配置；持久化verified仅在后端验证成功时设为true。

持久化采用两个小表，以外键保留清楚的关联，避免把提醒ID塞在JSON里：

- reminder_email_deliveries：一次真实发信任务。保存类型（due到点/offline_summary离线汇总）、收件人和主题/正文快照、配置修订号、发送状态、尝试次数、下次重试时间、错误、创建/发送时间。
- reminder_email_items：任务与reminder_occurrences的关联。delivery_id外键指向发送任务，occurrence_id外键指向实际提醒触发记录；同一触发记录只允许登记一次邮件。一个到点任务对应一条触发记录，一个离线汇总可对应多条记录。删除未发送的提醒后，发送前重新检查关联，只保留仍有效事项；没有有效事项就取消。

关系为：提醒规则 → 多条触发记录 → 通过关联表归入发送任务。设置页面只读后台权威状态，不因刷新新增任务；登记和去重通过数据库事务/唯一约束完成。

状态枚举：pending待发送、sending发送中、retry_wait等待重试、sent已发送、failed失败待手动重试、uncertain结果不确定、cancelled已取消。字段注释明确枚举；既有库使用正式v9迁移，升级前沿用一致性备份。

## 5. 失败、重启与重复处理

明确未发送成功的连接/网络错误最多自动尝试3次（初次加两次重试，间隔1分钟、5分钟），之后保留失败原因，由用户重试。账号、授权码或配置错误不反复自动尝试，提示修复并重新验证。

SMTP不是数据库事务，不能承诺网络断开时绝对只送达一次。例如服务器已经接收正文但确认响应丢失，应用无法确定邮件是否送达；这类任务标uncertain，不自动重发，界面说明后由用户决定是否重新发送。进程崩溃时仍为sending的任务，重启同样转uncertain，不盲目再次发送。

关闭邮件开关、修改邮箱或导入配置时，使旧配置下尚未开始的任务失效；后台发信前再次检查开关、绑定指纹和配置修订号，避免发往旧地址。

## 6. 依赖、备份与验证

使用固定版本lettre 0.11.23处理SMTP、TLS和邮件格式，复用现有异步任务、超时、配置加密、事务和中文错误体系；不自行拼接SMTP协议。依赖特性固定为builder、smtp-transport、tokio1-native-tls，不启用明文降级；旧库按009_reminder_email.sql迁移到v9。

全量备份可包含非密钥SMTP配置；不包含授权码、验证码、绑定有效性和待发送队列。导入后邮件开关关闭、绑定待验证，不重放历史邮件；重新填写授权码并验证后只登记未来提醒。人设/会话包不携带全局SMTP配置。

定向验证包括：配置变更使验证码失效、验证码过期/输错、无授权码不启用、任务唯一登记、循环提醒和离线汇总去重、发送失败不影响界面、崩溃恢复不盲目重发、导入不泄露凭据或重放邮件。用本机模拟SMTP验证工程流程，不使用用户真实邮箱作自动测试。真实SMTP服务、验证码收件和垃圾邮件情况由用户配置后实际确认。

实现依据：[lettre官方文档](https://docs.rs/lettre/latest/lettre/)、[SMTP传输配置](https://docs.rs/lettre/latest/lettre/transport/smtp/struct.SmtpTransport.html)。当前实现固定上述版本及特性，不使用开发分支。

## 7. 已实现的接口与文件

- `reminder_email.rs`：全局配置与密钥保护、输入校验、配置修订、验证码摘要与失效、导出公开配置；DTO不返回授权码。
- `reminder_email/outbox.rs`：触发事务登记、正文快照、删除来源后的重建、领用、有限重试、不确定状态及崩溃恢复。
- `reminder_email/transport.rs`：TLS/STARTTLS、SMTP连接和认证预检、提交前复核回调、纯文本邮件及中文错误分类。连接预检总超时30秒；提交总超时45秒；SMTP命令超时20秒。发送阶段未知I/O错误按uncertain处理，明确临时拒绝才有限重试。
- `reminders/rules.rs`在dispatch同一事务内将本次新触发ID交给enqueue；离线首次调度按同批合并，不另查历史生成邮件。
- `jobs.rs`复用现有循环调用tick，由Service的运行标记保证一次只发送一个任务；SMTP任务独立运行，不阻塞提醒事件或宠物计时。
- `ReminderEmailPanel.tsx`位于通用设置，复用主题Token及系统浏览器官方帮助入口。每5秒及聚焦时刷新发送记录，保留未保存草稿；不靠刷新登记邮件。

设置命令：`get_reminder_email`、`save_reminder_email`、`send_reminder_email_code`、`verify_reminder_email`、`set_reminder_email_enabled`、`retry_reminder_email`。均只对设置窗口开放。保存、启用、验证、重试携带当前revision；过期配置要求重新读取。验证码发送失败可能已保存连接配置，页面会读取真实修订号再重试。

提醒邮件只显示最近20个任务的状态；数据库保留完整记录。uncertain重发必须显式确认。关闭开关保留绑定和授权码，推进revision并取消旧待发任务；再次开启从新的enabledSince开始，不重发关闭期间历史。已开始提交或已被SMTP接受的邮件无法撤回。

## 2026-10-23 在线提醒话语与 v25

在线到点的 occurrence 在 dispatch 事务中直接成为 done，completed_at 为本次触发时刻，同时固定触发时的人设、会话、原提醒与人设正文快照。规则游标和邮件登记仍在同一事务里；一次性规则完成，循环规则保留下一次。

唯一 jobs 循环领取 pending 文案任务，调用当前聊天服务。请求使用已有非流式整次预算（默认300秒），没有额外30秒短截止；60秒只是宠窗展示时间。未配置服务、生成失败或异常中断恢复时使用默认话语，不改变已完成状态。已经进入 generating 的任务重启后不重复调用模型，以默认话语完成恢复；尚未开始的 pending 任务正常领取。

最终 presentation_text 与目标会话的一条 assistant 消息在同一事务保存，消息无用户回合，不虚构用户发言。只有触发时的会话接收；会话或人设被删除则不创建替代会话、不转投其他会话。提交成功广播 chat-messages-changed，宠窗订阅 reminders-changed 只读新话语，打开页面不发起润色。

邮件队列等待本次文案 ready 后再领用，正文包含相同角色话语及原事项、详情、原定时间。原 SMTP 重试/uncertain 规则不变。宠窗按钮为“知道了”，仅确认展示并收起；在线到点弹窗可见60秒，文本更新不重置时长，后台生成与邮件不被收起操作取消。

025_reminder_presentations.sql 为 occurrence 增加处理状态、触发人设/会话、输入快照、最终话语和消息关联，旧记录默认 legacy，不自动生成、不补聊天或邮件。完整逻辑备份保留最终文本和关联，导入的 pending/generating 转为 legacy，避免恢复后重放。邮件队列仍不进入备份。
